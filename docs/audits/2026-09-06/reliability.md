# BinDayNZ reliability audit — 6 September 2026

The core reliability gaps are calendar data safety, unverified address-to-schedule matching, date recurrence, and outputs that expire without replenishment. This review covers the current worktree, including existing uncommitted changes; no app source, project configuration or simulator state was changed by this reviewer.

## Evidence and reproducibility

- Run `sh docs/audits/2026-09-06/evidence/run_reliability_checks.sh` from the repository root. It compiles the actual `ScheduleEngine`, `BinType`, `Council`, `CollectionSchedule`, `CollectionZone` and `UpcomingCollection` files with host Swift 6.2.4/Foundation. Only localization is substituted to avoid modifying the host's language preferences. Build artifacts are temporary.
- [Recorded output](evidence/reliability-checks.txt): **2 of 9 desired invariants passed; 7 failed; exit status 1.** Four failures are odd/even variants of the same recurrence defect. Both NZ DST checks passed. The timezone check explicitly tests the proposed requirement that schedules remain attached to the NZ property.
- Widget lifetime and reminder counts use the actual engine with the current payload-window policies. They do **not** execute WidgetKit or UserNotifications. Root-owned iOS runtime evidence should be assessed separately.
- [Public council endpoint matrix](evidence/council-endpoints.json), generated by [this script](evidence/check_council_endpoints.py), checked two app sample addresses, one nonexistent address and one unit variant at **2026-09-06 09:43 UTC**. All four returned HTTP 401. No private profile was read, and no authentication barrier was bypassed.
- Source references below are repository-relative and use the line numbers inspected on this date. “Source-confirmed” means the control flow is established; it does not imply the failure was triggered on an iPhone.

## Release priorities

### R1 — P0: Calendar sync can delete unrelated events

**Source-confirmed:** `BinDayNZ/Services/CalendarService.swift:123–147` reuses any calendar named `Bin Day NZ`, or returns the user's default calendar if creating the dedicated calendar fails. `:40–43,153–164` then deletes all matching events in the selected calendar over the next six months. `:62–66` also removes a calendar by title alone. Deletion errors are suppressed; new events are saved individually afterward (`:48–57`).

**Reproduction:** In an isolated calendar store, create an unrelated calendar named `Bin Day NZ` with a future personal event; enable sync. Separately inject dedicated-calendar creation failure while a writable default calendar exists. Neither path requires an event to carry an app ownership marker before deletion. Root owns the isolated runtime reproduction; this reviewer did not access personal calendars.

**Impact:** Unrelated calendar events can be erased. A later save failure can also leave previously synced collection events deleted or partially replaced.

**Recommendation:** Remove the default-calendar fallback and title-based ownership. Persist the app-created calendar identifier, track app-owned events, and fail before deletion if calendar creation or ownership verification fails. Reconcile only app-owned events and preserve the previous valid export until replacement can commit.

**Acceptance:** A same-title unrelated calendar, unrelated events added to the app calendar, denied access, unwritable source and a failing event save all retain unrelated data. Repeated sync produces one event per intended collection; disabling sync removes only app-owned content.

### R2 — P1: Fortnightly recurrence changes at year boundaries and with calendar rules

**Observed using actual engine:** `ScheduleEngine.swift:44–51` bases fortnightly collection on `weekOfYear % 2`. The audit produced:

| Calendar scenario | Observed dates | Actual gap |
|---|---|---:|
| ISO, odd weeks | 28 Dec 2026 → 4 Jan 2027 | 7 days |
| ISO, even weeks | 21 Dec 2026 → 11 Jan 2027 | 21 days |
| Gregorian `en_NZ`, odd weeks | 25 Dec 2028 → 1 Jan 2029 | 7 days |
| Gregorian `en_NZ`, even weeks | 18 Dec 2028 → 8 Jan 2029 | 21 days |

For **4 Jan 2027**, an odd-week schedule returns no recycling with the tested `en_NZ`/`en_US` calendars but returns recycling with `en_GB`. This is a device-calendar-rule difference, not proof that changing the app's own language picker changes calendar rules.

**Impact:** A saved fortnightly schedule can skip or add a collection week despite no change in the property's service.

**Recommendation:** Replace week parity with a confirmed per-bin collection-date anchor and 14 calendar-day recurrence in an explicit property calendar. Preserve date exceptions independently from the regular pattern.

**Acceptance:** Odd/even legacy concepts are removed from the active calculation; every regular fortnightly interval remains 14 local calendar days across year boundaries and locale changes. Test the examples above and a full leap-year interval.

### R3 — P1: The council lookup currently fails from this host, while the app silently retains an inferred schedule

**Observed network result:** The production property endpoint returned HTTP **401** for `12 Queen Street, Auckland`, `4 Figaro Street, Ponsonby`, `999999 Audit Example Road, Auckland`, and `1/12 Queen Street, Auckland`, with `{"error":"Authorisation error. Current IP address logged."}`. The first sandbox request failed DNS resolution; an authorised read-only network retry reached the server. This is evidence about this host/request path, not every iPhone or network.

**Source-confirmed:** `AddressSearchService.swift:73–105` first selects a suburb zone and silently retains it when live lookup fails. `:194–206` ignores the HTTP response status and chooses the first property without checking its returned address. The 401 JSON can decode with missing optional `items`, producing no live zone. The selected-zone UI does not label this result as an unverified suburb estimate (`AddressSearchView.swift:326–346`).

**Impact:** A successful MapKit address match can be presented alongside an unrelated or stale collection schedule. An invalid/ambiguous address can receive the first property result if the endpoint returns candidates.

**Recommendation:** Confirm the supported source/access contract before depending on the endpoint. Validate HTTP status and returned property identity; require explicit user confirmation for an ambiguous property. Distinguish verified dates, user-entered schedules and unavailable lookup. Remove silent suburb-based schedule assignment unless its correctness has been established for the exact property.

**Acceptance:** A public sample matrix covers exact addresses, units, street boundaries, no matches, HTTP 401/429/500 and offline operation. The selected property and official dates agree; failures produce an honest recovery state without an apparently confirmed schedule.

**Limit:** No property IDs were returned, so current schedule-page HTML, its date fields and regex compatibility were **not verified**. No claim is made that the regex currently works or fails on an accessible official schedule page.

### R4 — P1: Date parsing loses exceptions and service-specific information

**Source-confirmed:** `AddressSearchService.swift:220–260` parses only `Rubbish` and `Recycling`, assigns the current year to a month/day, takes rubbish's weekday and recycling's parity, then selects a bundled template. `CollectionSchedule.swift:16–23` cannot represent explicit dates, exceptions, source timestamps or expiry. Bundled dynamic zones supply food scraps without this parser verifying a food-scraps date.

**Reproduction:** A next collection in January fetched in December is assigned to the current calendar year. A one-off shifted collection is converted to a repeating weekday; differing rubbish/recycling days cannot survive the single-weekday template lookup. These are source-derived scenarios; the current live page could not be retrieved through the API matrix.

**Impact:** Even a successful request can produce misleading future dates, especially around service changes or holidays.

**Recommendation:** Keep confirmed per-bin dates and their provenance. Infer regular recurrence only from an authoritative rule, and preserve exceptions. Check freshness when returning to the app and show when the underlying schedule was last verified.

**Acceptance:** Fixtures for Dec→Jan, holiday shifts, missing service fields and different per-bin weekdays preserve the supplied dates. Today, calendar, reminders and widget agree for every fixture.

### R5 — P1: Reminder generation is finite and scheduling failure is invisible

**Observed generation:** The actual engine with the bundled Auckland Monday schedule, starting 6 Sep 2026, supplies 60 bin events through **22 Feb 2027**. Applying the current evening/morning policy generates **120 one-shot notification requests**. This calculation does not establish how many requests a modern iOS runtime retains.

**Source-confirmed:** `NotificationService.swift:78–124` cancels every pending reminder before adding replacements. `:65–69` only prints asynchronous add errors. Callers cannot await or report successful scheduling. Refresh callers are setup, settings changes and address changes; no launch/foreground replenishment was found in `BinDayNZApp.swift`, `ContentView.swift`, or the service callers. The app does not inspect pending-request coverage.

**Official documentation:** Apple documents a 64-request limit in the **deprecated** [`UILocalNotification`](https://developer.apple.com/documentation/uikit/uilocalnotification) documentation. It is evidence of a capacity concern, not a measured current `UNUserNotificationCenter` limit. Current [notification scheduling documentation](https://developer.apple.com/documentation/usernotifications/scheduling-a-notification-locally-from-your-app) explains system delivery, one-shot versus repeating triggers, and cancellation; the reviewed current page does not state that capacity. Measure pending requests through the supported API.

**Impact:** Reminders eventually stop without the user changing anything. Partial replacement failure can remove working reminders while the UI still shows them enabled.

**Recommendation:** Group same-date bins into one reminder, await and verify scheduling, and expose permission and coverage state. Use an explicit renewal policy that covers low-frequency app use; reopening should reconcile the current schedule and settings. Do not rely on a background task being guaranteed to run.

**Acceptance:** Inspect pending counts and earliest/latest dates on the supported OS, exercise add failure and permission revocation/regrant, test same-day multiple bins and long inactivity, and demonstrate actual foreground/background/terminated delivery. Root owns these runtime checks.

### R6 — P1: Widget data expires after weeks and displays a false empty state

**Observed payload behavior:** For the 6 Sep snapshot, `WidgetDataService.swift:15–18` supplies 12 events ending **5 Oct 2026**. On **6 Oct**, the provider's filtering policy yields zero events even though the actual engine still supplies collections from **12 Oct** onward. `BinDayNZWidget.swift:98–115` only filters the stored snapshot; its daily refresh does not create new collection dates. `WidgetViews.swift:19–29` displays “No upcoming collections” with a checkmark after exhaustion.

**Impact:** The widget can incorrectly suggest there is nothing to put out after about a month of normal use. Relaunch alone does not update the payload; source callers only refresh at setup, address change and language change.

**Recommendation:** Share the current schedule and verified data state with the extension, allowing its timeline provider to calculate future entries independently. Supply predictable date transitions in the timeline. Distinguish expired or unavailable data from a confirmed no-collection state.

**Acceptance:** Advance beyond the initial 12 entries without opening the app; all supported widget families still show correct collections or an explicit stale-data state. Verify midnight, changed address/language, malformed payload and device timezone changes. Apple's [WidgetKit guidance](https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date) recommends timelines for predictable events and notes budgeted, noncontinuous extension execution; requesting a daily reload is not a replacement for renewable data.

### R7 — P1: Address changes can leave profile, reminders and widget inconsistent

**Source-confirmed:** `ChangeAddressView.swift:396–408` mutates/saves the profile, then reschedules reminders, then awaits calendar sync, then refreshes the widget. If calendar sync throws, `:410–412` reports failure while the new profile and reminders remain committed and the widget remains old. `OnboardingContainerView.swift:75–83` likewise ignores the final profile-save error after marking onboarding complete.

**Impact:** The user's recovery action can operate on a different address than the one the error implies was saved; different surfaces can disagree about collection day.

**Recommendation:** Make profile-save success distinct from external integration status. Commit one valid profile, update independent consumers from that same saved snapshot, and report/retry failed integrations without implying the address was not saved. Handle persistence errors before completing onboarding.

**Acceptance:** Revoke calendar permission before changing an address; all in-app and widget data use the new saved schedule, with a precise calendar error. Inject profile persistence failure; no success state or externally scheduled replacement should be reported as committed.

### R8 — P2: Manual schedules cannot represent mixed bins or recover outside Auckland cleanly

**Source-confirmed:** `ManualScheduleView.swift:89–101` applies one weekday/frequency/parity to every selected bin. The editor initializes defaults rather than receiving the saved schedule (`:6–9`). `CouncilPickerView.swift:48–71,109–115` only permits councils with bundled zones; currently only Auckland qualifies. Manual setup lives after that council selection. `ChangeAddressView.swift:34–50,396–400` continues to use the saved council and does not update it.

**Impact:** The fallback cannot faithfully enter weekly rubbish plus fortnightly recycling; editing can overwrite the prior configuration with defaults. A resident elsewhere must select Auckland to reach manual setup, producing misleading location metadata.

**Recommendation:** Edit day, cadence and a concrete next collection date per selected bin. Prefill saved values. Make manual setup available without selecting an unsupported council under a false identity, and make changing council part of changing location.

**Acceptance:** Save/reopen/edit different cadences and days per bin; clear all bins; enter a Sunday schedule and a next date after this week's collection; complete an honest manual setup outside Auckland.

### R9 — P2: GPS lookup drops street names and can leave pending requests unresolved

**Source-confirmed:** `LocationManager.swift:47–53` appends the street number but only appends the street name when the number is nil. A numbered address can become `12, Ponsonby, Auckland`. A single continuation is replaced without rejecting a concurrent request (`:34–36`), while location buttons remain tappable (`AddressSearchView.swift:202–224`). `locationUnknown` returns without resolving the continuation or retrying (`LocationManager.swift:79–87`). These callback/concurrency failure scenarios were not triggered on hardware.

**Impact:** GPS assistance weakens address matching; repeated taps or an unavailable location can leave a spinner/request waiting indefinitely.

**Recommendation:** Join nonempty street-number and street-name components. Allow one active location request, and complete every success/failure/cancellation path exactly once with an actionable error when no location is available.

**Acceptance:** A numbered placemark retains both components; denied, restricted, no fix, reverse-geocoder failure and repeated taps settle predictably and leave manual address entry available.

### R10 — P2: CloudKit update code is disconnected

**Source-confirmed:** `CloudKitService.swift:96–101` has no caller outside its own file. `:79–87` writes `councils_updated.json`, but `DataService.swift:23–42` only reads bundled `councils.json` and caches it. App entitlements contain app-group access, not CloudKit configuration. The code also compares against the bundled version rather than an applied remote version (`CloudKitService.swift:21–33`).

**Impact:** The current code does not deliver schedule corrections without a new bundle or address lookup, despite an apparent update service existing.

**Recommendation:** Remove the unused update service unless it is the chosen supported data-distribution route. If it is retained, connect versioned download, validation, durable activation and downstream refresh end to end; test the actual deployed capability before describing updates as supported.

**Acceptance:** A controlled newer dataset is used by every consumer after activation and relaunch; malformed/older data does not replace a valid schedule. Otherwise no dead updater or update claim remains.

### R11 — P2: Calendar export is a finite snapshot with interoperability gaps

**Source-confirmed:** `CalendarService.swift:73–106` emits finite events rather than a subscription, omits `DTSTAMP`, and constructs text using line feeds and unescaped localized values. Its `count: 90` is a count of bin events, not three months (`:45–46,74`). No automatic calendar renewal exists in the callers. Event `DTSTAMP` is required by [RFC 5545 §3.6.1](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.6.1); the same specification defines text escaping and content-line syntax. No import failure was measured in this review.

**Impact:** Users may interpret sync/export as ongoing; strict clients may reject or misinterpret the file. Calendar coverage silently runs out.

**Recommendation:** Describe `.ics` as an export, state its date coverage, and generate standards-compliant text using a focused, validated exporter. Make Apple Calendar renewal behavior explicit and reconcile only app-owned events.

**Acceptance:** Validate/import the file in supported calendar clients, including translated labels, punctuation and long descriptions; verify event count/dates, duplicate imports and coverage expiry.

## What passed and what remains unverified

The engine's use of calendar-day arithmetic preserves midnight and seven local days across NZ DST changes: **169 elapsed hours** at DST end and **167** at DST start. Replacing this with fixed-second arithmetic would regress that behavior. The collection models and engine compiled successfully in the audit harness.

The same instant at **7 Sep 2026 00:30 in Auckland** is **6 Sep in Los Angeles**; the current engine classified it differently under those two device calendars. That is an observed result with a product-policy implication: a NZ property's schedule should use its location timezone, while reminder display/time policy should be explicit. It is not evidence of a DST arithmetic bug.

No device notification delivery, modern OS pending limit, physical GPS accuracy, actual WidgetKit rendering, personal calendar mutation or CloudKit deployment was tested by this reviewer. No successful council property response or authoritative date comparison was obtained. All remain separate acceptance evidence, not reasons to discount the source-confirmed defects. The app should reconcile saved data and permission state on foreground activation; Apple's [scene lifecycle documentation](https://developer.apple.com/documentation/swiftui/scene) supplies the supported `scenePhase` hook, but does not promise execution while the app is terminated.
